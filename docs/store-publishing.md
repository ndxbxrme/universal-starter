# Store publishing and client approval

No store submissions or account changes have been performed. Current template identities/support links must be replaced and reviewed before release. A successful signed build is not proof of store acceptance, account permissions or privacy compliance.

Google Play: the client owns Play Console access, permanent app ID, upload key/recovery contacts and Play App Signing enrollment. Complete store listing text/icons/screenshots, support/privacy URL, content/audience ratings, data safety and applicable policy declarations. Increment Android versionCode, build a signed AAB, verify signature/fingerprint continuity, and upload through Play Console to internal testing first. Review processing/tests and tester eligibility, then promote a staged production rollout with client approval. This implementation provides artifacts and manual instructions rather than an unconfigured upload action.

Apple: the client needs Apple Developer membership and App Store Connect access with appropriate roles, a matching registered bundle ID, certificates/provisioning/export workflow and app record. Review screenshots/listing, privacy details/manifest, support/privacy policy, age rating, export compliance and any account-specific agreements. Archive/export on macOS, verify codesign and real-device behaviour, then use Xcode Organizer/Transporter to upload to App Store Connect. TestFlight processing and external testing may require review. Submit/promote only after client approval. Simulator output never substitutes for a signed IPA.

Desktop outside stores: sign Windows installers using the client's supported OS certificate store/provider, and sign/notarize macOS with Developer ID through approved Keychain references. Verify actual exported signatures/Gatekeeper assessment on each target. Review license files, installer permissions, checksums, platform naming and manual-update guidance before publishing GitHub Release assets. Linux package signing depends on chosen distribution policy.

Production rollback on mobile generally means a newer fixed version/build, not downgrading installed apps. Halt a staged rollout if needed and ship a forward fix. Keep previous artifacts, source commit association, public fingerprints and release notes. Never rotate/recreate a client's production key as a shortcut. Follow credentials.md for expiration/recovery/handoff.
