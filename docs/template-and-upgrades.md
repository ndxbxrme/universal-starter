# Template ownership and future upgrades

V1 is a versioned configurable template, not a generator/updater CLI. universal-app.config.json is the canonical non-secret app metadata; schemas/universal-app.schema.json validates it. .universal-app.json records schema/template versions, project UUID, initialized native identity and applied migration IDs (empty in V1). It has a separate schema. Credentials are never metadata fields. Runtime adapters do not depend on future CLI code.

`npm run setup` idempotently syncs metadata, icons and license notices. For a new client, assign a fresh version-4 UUID in .universal-app.json or use setup's explicit --project-id UUID --new-project options; repeating the same UUID is idempotent. This changes provenance only, not native IDs/signing assets. Do not reset another client's provenance during handoff. Credential reference storage is scoped by both UUID and app ID.

App-owned: src/app/**, src/features/**, src/main.js and business logic/styles customized for the product. Starter-owned: src/platform/**, shared script implementations and their contract tests. Shared/review-required: native projects, package/lock files, config, Vite/Electron/Capacitor settings, workflows, tests and docs. Generated assets are listed in resources/README.md. config:sync patches only documented metadata fields in these shared files and refuses changed identifiers; it is not permission to overwrite an entire directory.

config:sync stages/validates changes before writing, supports --dry-run and is repeatable. Review its git diff. It controls package name/version/homepage/desktop association, Capacitor identity/name/webDir, Android version/name strings, iOS version/display name, and generated branding CSS. Native identifiers remain stable unless a separately reviewed migration is completed. Native source, team settings, custom permissions and business logic are not regenerated by metadata sync. Native build numbers must be managed monotonically for existing store installations.

Future architecture may separate a runtime core, a versioned starter template and a thin create/update CLI, but no such packages are mandatory in V1. V2 could add safe project creation with interactive/non-interactive and dry-run modes. V3 could add ownership-aware migration manifests, backups, conflict reports, approval and rollback. Blind overwrite upgrades are explicitly excluded. Until then, compare template versions on a branch, port reviewed file-level changes, preserve client-owned logic/credentials, and run the full verification matrix before merging.
